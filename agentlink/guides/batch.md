# batch: run tools in one call
<!-- SPDX-License-Identifier: LGPL-2.1-or-later -->

The whole text of batch's description, kept here for ToolListMode static with ToolDescStyle ste (its listed description is short). Nothing is left out.

## Start here
- The basic form: `batch { calls: [ { tool: "sketch_new", arguments: { plane: "XY" } }, { tool: "sketch_add", arguments: { items: [ { kind: "rectangle", center: [0, 0], size: [40, 20] } ] } } ] }`. Give only calls for a first batch; the other fields are for later.
- The calls run one at a time, in order: a call sees what the calls before it made. They never run at the same time.
- Read `calls and rollback` and `chaining` first. Read the others when their moment comes.
- The most common error: a name or an id typed from memory. Take it from an earlier call with `{ "$from": i, "$at": "path" }`.

## calls and rollback
Run several tools in one call, one at a time, in order: calls [{ tool, arguments }], or path: a .json file holding that list (or { calls, rollback, stopOnError }), read on this side so a long run of calls (many profiles' points) is not sent through the conversation; a relative path is in the session's folder, and files are read where other tools may read. The first refused call stops the rest (stopOnError: false runs them all). The calls before it stay, each its own undo step. The answer carries done (the calls that ran), refused ({ call, tool, code, kind, error }) and notRun, all counted from 0 through the whole list, and next, the refused call. The note names the calls to send next: a new batch with the refused call fixed and the calls in notRun, with no start (start counts in the list you send; it is for path: batches). result says what the batch left: kept, ran_none, rolled_back or partial; each refused call's status says what it left: not_started, rolled_back or cleanup_incomplete. A call with a wrong form (no tool, a tool that does not exist, arguments that are not an object, an unknown field) is refused by itself when its turn comes; the calls before it run. A form error of the batch itself (calls and path together, a bad budget or start) refuses the whole batch, and nothing runs. rollback: true makes the batch stand or fall whole: at a refusal it undoes what the batch changed before it and removes every object it made (removed lists any undo did not reach), and a call with a wrong form refuses the batch before anything runs. Limits: with rollback, at most as many changing calls as FreeCAD keeps undo steps (20 by default); a heavy read (a tool that runs as a job on its own: a wall-thickness or deviation reading) runs as a job inside the batch too, and the batch waits for it while its budget lasts — still running then, the answer carries the job id (job_status gives its answer) and where to go on; no call starts past budget seconds (55 by default, at most 100) — the answer then carries notRun and next, what ran stays, and the note names the calls to send in a new batch (with path: the same file and start: next).

## health and timings
Each changing call's result carries its own health; a batch does not run another batch. A call whose surroundings took long (500 ms or more round the tool itself) also carries around { wall, outside { ms, echoBefore, echoAfter, fit, callDone, notice, meter, record, other }, inside { healthMark, health, snapshot, undoStep, afterChange, outputs }, tool } in ms: wall is the whole call, outside what its own ms does not count (the echo in the window and its view fit, add-ons told of the call, this batch's record), inside the hub's share of its ms (the health check before and after, the step kept for history_diff, the undo step, add-ons told of the change), tool what is left for the tool — read it before deciding a document is too slow to work in.

## the window pace
In the FreeCAD window each changing call is shown as it runs (its workbench, its button lit, its result selected) with a pause so a person can follow, which costs about 0.4 s and up to 2.5 s a call: a long batch runs faster from its fourth changing call on — those are still shown, with a pause of 60 ms (the person's EchoBatchDelay preference, ms; 0 none, -1 the full pause throughout) — and its last changing call is shown at the full pace again, so the window ends on a state that can be read; one batch of 20 calls is therefore much quicker in the window than 20 calls sent singly.

## writeTo, lines and records
writeTo: a .json file the whole answer is written to (relative: in the session's folder); the reply is then a line per call — ok, a refusal's words, the health verdict (a verdict's standing part, "N objects still failing from before this call: …", is given at the first line it shows in and again only when it changes; healthNote says so when it was left out of later lines, and a line that had nothing else reads "as before") — and keeps the batch's own note beside it (where it stopped and how to go on: next, notRun, heavy), so a long run's answers stay out of the conversation; read a call's result from the file when its line needs it. Every batch also keeps what ran in a record of its own, batches/<date>-<time>.json in the session's folder (the reply's record is its path; the newest 20 are kept), rewritten as each call ends: when a batch's answer never arrives — a call the client dropped, FreeCAD stopped and started again — read the newest record to see which calls ran (running: true and ran: n while it was under way, each call's whole result in results) before running anything again.

lines: "refused" (with writeTo): the reply lists only the calls that were refused or whose health is not clean, with counts { ok, refused } for the rest — for a long run whose answers are read from the file; "all" (the default) keeps a line per call; "counts": the counts alone. A batch from a file answers that way without writeTo too, from its record (written names it; a line per call unless lines says otherwise), and so does a batch of calls given lines; lines: "full" gives every call's whole answer in the reply instead (with writeTo, written there as well).

title: a few words for the person; kept in the record.

## chaining
Chaining, so an answer one call needs from another does not pass through the conversation: (1) a call may carry writeTo — { tool, arguments, writeTo: "outline.json" } writes that call's whole answer to the .json file (relative: in the session's folder; written where tools may write) and its result here is only { written: { path, bytes }, keys (an object's) or length (a list's), and health when it had a verdict }; a refused call writes nothing, and a rollback leaves the files. (2) Anywhere inside a call's arguments, { "$file": "outline.json" } is replaced by that JSON file's contents and { "$file": "outline.json", "$at": "loops.0.points" } by the part at that dotted path of keys and list indices (from 0; -1 is the last); the file is read as the call is about to run, so it may be one an earlier call of this batch wrote, and is read where tools may read. (3) { "$from": 2, "$at": "bodies.0.name" } takes the same from the answer of call 2 of this batch (calls are numbered from 0 through the whole list, as start and next count; only an earlier call, and only one run in this part of the batch — across parts use writeTo and $file). A reference stands alone as the value ($file or $from, with $at); one that cannot be followed — no file, no key, no index, a refused call — refuses that call, saying what is there (the keys or the length at the deepest level reached), and counts as a refusal for stopOnError and rollback; a file or answer over 20 MB is refused. The arguments are checked after the references are filled in.
- Example: `batch { calls: [ { tool: "session_state", arguments: {} }, { tool: "steps_list", arguments: { body: { "$from": 0, "$at": "bodies.0.name" } } } ] }`.

## build end
build: "end" recomputes once for a run of changes instead of after each: while consecutive calls are sketch_add, sketch_constrain, sketch_edit, sketch_offset or object_set on one document (and any tools an add-on declares safe), FreeCAD's recompute is held (its own Skip recomputes switch), and the document is built once — at the end, before the first call that is none of these (a read that needs geometry, a pad: they build first and run as always), or when a call moves to another document. A held call's answer carries build: "held" and a health that says the reading is held; the parts of its answer read from the rebuilt shape (a sketch's wires, closedWires, openVertices and readyForFeature, sketch_edit's bodyAfter) are left out and named in health.leftOut — a sketch's solver, dof, conflicting and redundant are still fresh. builds [{ when, held, calls: [first, last], recomputed, ms, health }] in the batch's answer carries the one health reading for everything the held calls made or changed. A held call cannot refuse for what only a rebuild shows (an edit that breaks a later feature): when a build leaves an object failing that was not before, the batch stops there as at a refusal (buildFailed: true) and, with rollback: true, is taken back whole. guide_read, tool_groups, usage_report and job_status run inside a held run without a build. If the person has Skip recomputes on already, nothing is held or built and buildNote says so. Use it for a sketch drawn and constrained in many calls or many properties set; leave it out when each call's own reading matters.

## record_read
record_read { path, at }: path is a .json file (a batch's record or a writeTo file), at a dotted path in it ("results.3.result"; results count from that part's first call). It answers that part ({ path, at, value }) and changes nothing — the way back to any answer a reply left out.
