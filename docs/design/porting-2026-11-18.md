# Porting add-ons to Agent Link (design, 18 Nov 2026)

Status: built on main. Written in ASD-STE100.

## Goal

A person has a FreeCAD add-on. The add-on has no Agent Link tools.
Give the person and the agent three things:

- A. A porting guide that `guide_read { topic: "porting" }` reads.
- B. A scaffold. It reads an installed add-on and writes a draft port.
- C. Cookbooks. A cookbook is data: entries that run the add-on through
  the runners that exist.

## A. The porting guide

File: `agentlink/guides/porting.md`. The guide index finds it. No code.
The guide has these sections:

1. Start here (the order of the work).
2. The hook file (`agentlink_families.py`, the family module).
3. The tool data (`tools.json`, the fields, the format check).
4. STE rules (20 words or fewer in a sentence, one instruction a sentence).
5. Refusals (a code and a message with the next step).
6. The core (no `agentlink` import in the add-on's core).
7. Tests (alone, with Agent Link, the import check, the lint).
8. The privacy check (no names, no home paths, no secrets).
9. Cookbooks (when a cookbook is enough, and when a port is better).
10. Agent brief (a block of text to give to another agent).

The guide names no add-on. `tests/test_no_addon_names.py` checks this.

## B. The scaffold

Code: `agentlink/porting.py`. Plain Python, no FreeCAD, no Agent Link
import. It runs in three ways:

- The tool `port_scaffold { folder, name?, overwrite? }`.
- `python3 -m agentlink.porting <folder>`.
- `python3 <hub>/agentlink/porting.py <folder>`.

It reads the add-on's Python files as text with `ast`. It never imports
and never runs the add-on's code. It finds each `Gui.addCommand(name, obj)`
and the `GetResources` of the command's class (`MenuText`, `ToolTip`).

Output: `~/AgentLink/ports/<name>/` only. The scaffold refuses an output
folder inside the add-on or inside Agent Link. It writes:

- `README.md`: what is there and the next steps.
- `hook/agentlink_families.py` and `hook/fam_<group>.py`: the hook.
- `hook/data/tools.json`: one draft entry for each command.
- `hook/api.py`: the core stubs (no `agentlink` import).
- `tests/test_port.py`: the format check, the handler check, the import
  check and the lint.
- `scripts/ste_lint.py`: the lint, plain Python.
- `cookbook.json`: a draft cookbook with one command recipe a command.

## C. Cookbooks

One file for each add-on: `~/AgentLink/cookbooks/<name>.json`.

```json
{"cookbookVersion": "1.0.0", "name": "mine", "about": "…",
 "addon": {"package": "mine"},
 "entries": {
  "mine_do": {"description": "…", "recipe": {"command": "Mine_Do"}},
  "mine_fit": {"description": "…", "recipe": {"python": {"module": "mine.api",
    "function": "fit", "args": {"type": "object", "properties": {"gap": {"type": "number"}}},
    "document": true}}},
  "mine_steps": {"description": "…", "recipe": {"script": {"calls": [
    {"tool": "session_state", "arguments": {}}]}}}}}
```

The runners:

- `command`: `cmd_run { name, index }`, with all of its refusals.
- `python`: the function `module.function(**args)`. The module must be the
  add-on's package or a module in it.
- `script`: a list of Agent Link calls, run by `batch` with rollback.
  `file` names a JSON file in the cookbook's own folder.

The tools (group `porting`, not lean, not in the static base):
`cookbook_list`, `cookbook_show`, `cookbook_import`, `cookbook_export`,
`cookbook_approve`, `cookbook_unapprove`, `cookbook_run`.

### Approval

- The store is the approved-macros store: `~/AgentLink/macros-approved.json`.
  A cookbook key is `cookbook:<name>`. A macro name cannot hold `:`.
- The hash is SHA-256 of the cookbook file and of each script file it
  names, in name order.
- `cookbook_approve { name }` shows the OK dialog in the FreeCAD window.
  The person presses Approve there. No tool can press it, and a typed
  confirm is not taken (red team, 2026-11-18: an agent could type the
  words itself). Headless, the OK is refused. See `agentlink/person_ok.py`.
- A changed file (hash mismatch) needs the OK again.
- An unapproved or changed cookbook: `cookbook_list` lists its entries.
  `cookbook_run` refuses each entry with the next step.
- No entry runs code without the OK. Command recipes also need the OK.

### Against the red team

| Attack | Defence |
|---|---|
| Code runs without an OK | Every recipe kind needs the OK. The check is in `cookbook_run`, before the runner. The OK is a press in the window that no tool can make (`agentlink/person_ok.py`). |
| Approval bypass | The hash covers the file and its script files. A script call to a `porting` tool, to `batch`, to `job_start` or to a tool name with `approve` is refused. Writes by tools to the store or to the cookbooks folder are refused (`paths.check`). |
| Path escape | Names match `^[a-z][a-z0-9_]{1,47}$`. A script file must be in the cookbook's folder after `realpath`. Import reads files only next to the source file. |
| Prompt injection | Descriptions are data. They are capped at 400 characters, one line, no control characters. Answers mark them as the author's words. |
| Name takeover | Entries are never tools. An entry name equal to a tool name is refused on import and refused on run. A cookbook name that is there already needs `overwrite: true`, and then the OK again. |
| Module reach | A python recipe's module must be in the add-on's package. The package must not be a standard library module, `agentlink`, or FreeCAD's own. The package must be in a Mod folder (an installed add-on, not site-packages). Function names that start with `_`, and names of an OK (approve, grant, confirm), are refused. |
| Size | A file holds 256 KB or less, 200 entries or less, 100 script calls or less. |

### Cost

The base listing does not change. The new tools are in the `porting` group.
This group is not lean. With no cookbook installed, nothing more is read
at start.

## D. Cookbook format 2: a socket with instructions (18 Nov, later)

Goal (18 Nov): a data-only add-on port that runs headless. Use the
same method as for FreeCAD's core: inventory, judge each item, probe, bars.
"80 %" is a direction, not a target. Measure each add-on.

Two doors:

- The standard. The add-on's author ships the cookbook to this format.
- The auto-port. An agent follows the rules in the guide (`auto-port
  rules`) and writes the same file. `port_scaffold` writes the draft.

Code: `agentlink/cookbook2.py` (the format, inputs, conditions, checks,
bars), `agentlink/addon_scan.py` (the static scan), `agentlink/cookbook_fc.py`
(the FreeCAD side: state, picks, scratch document, form fill). The store,
the OK and the tools stay in `agentlink/cookbook.py` and
`agentlink/families/porting.py`.

### Levels (try them in this order)

| Level | Call | Runs |
|---|---|---|
| 1 data | `function` {module, name, document} | the add-on's function, headless |
| 2 form | `form` {command, fields, accept} | the task panel, fields set from data, OK pressed |
| 3 tree | none; `tree` of branches | nothing: it gives the next entry |
| 4 window | `command` | `cmd_run`, as the button |
| 5 not supported | none; `blocker` | refused with the blocker; tried again on a new version |

### Entry fields

level, description, call, inputs (type, unit, min, max, default,
required, choices, count, as), preconditions (workbench, document,
selection, objects), result (makes, check), tree (when, next, say, needs),
risk, probe (version, result, date, why), source (from, checked), blocker.

### What Agent Link works out itself

- risk: from the call. A function: the static scan of its module and of
  the add-on modules it imports. A command or form: the file that
  registers the command. What cannot be read counts as code. The file's
  `risk` is shown as `riskClaimed` only.
- coverage: counts per level, declared and proven. Proven is a pass of
  Agent Link's own probe at the installed add-on version (package.xml).
- probe: `cookbook_probe` runs each level 1 entry in a hidden scratch
  document, with defaults and a Part box for picks. `cookbook_run` records
  its result too (levels 2 and 4 need the window). The records are in
  `~/AgentLink/cookbook-probes/<name>.json`, apart from the file, so a
  probe never changes the file's hash (the OK). `cookbook_export` puts
  them in the shared file.

### Guards (an add-on built to be ported may try to take over FreeCAD or the Mac)

Add-on code runs with the person's rights. The OK (approve_code) is the
wall. The cookbook opens no new door:

| Attack | Defence |
|---|---|
| A call that reaches os, subprocess or FreeCAD | The module must be in `addon.package`; the package must be in a Mod folder; no standard library, FreeCAD or Agent Link package. |
| An add-on module re-exports os.system or shutil.rmtree | One look-up in the module's own namespace (no getattr chain, no module `__getattr__`). The function must be plain Python with `__module__` and its code file in the add-on package. |
| sys.modules spoof (`sys.modules["pkg.x"] = json`) | The loaded module's file must be in the add-on package folder. |
| Code in a condition | Conditions are data: compare an input, count a selection, all/any/not, 4 levels deep. Anything else is refused at import. |
| Out-of-range input | Each input is type- and limit-checked before the call. Names are plain; `__class__` and extra inputs are refused. |
| Form clicks a button | A form sets input widgets only (spin boxes, fields, check boxes, combo boxes). All fields are found first; one missing field sets none and closes the panel with Cancel. Only OK, Apply or Close is pressed. |
| Prompt injection | Descriptions, says and blockers are capped, one line. Words like orders to an agent are flagged in each answer and in the OK dialog. |
| Data leak through a result | Results are filtered: ~ for home paths, keys and tokens hidden, an object of another document is a mark only. Error text is filtered too. |
| Hidden reach | `addon_scan` flags network, subprocess, dynamic code, encoded code, secret files, environment, sys.path, file writes, other documents and settings. The words go into the pending OK: "This add-on calls the network." |
| Forged probes | Probes are in Agent Link's own folder; `paths.check` refuses tool writes there. A file's probe and coverage are claims only. |

The approval layer (agent "perms", same day) may move the OK to
approve_code. Every runner asks one helper: `cookbook.is_approved(name, sha)`.

### Live 95 and 96

- 95: level 1 drafts only functions that look like an API. Each has a
  docstring, typed or documented arguments, no window, thread or callback
  argument, and work on document objects (a doc argument, a pick, or
  addObject, recompute, .Shape). Its module is not glue (__init__,
  commands, workbench, fam_*) or window code (panel, sidebar, layout, gui).
  Plumbing names (get, list, app, own, runner, caller, on_*, *_gui …) are
  out. The rest is in the answer's `internal` list, with why, not entries.
  Texturizer: 30 level 1 drafts became 2 (make, convert); 446 internal.
  Workshop: 20 became 6; 309 internal.
- 96: cookbook_show took 49 s on Texturizer. The scan now reads the add-on
  once into an index (flags, imports, command files), kept in memory and in
  ~/AgentLink/cookbook-scans/ by the folder's fingerprint (paths, sizes,
  change times, package.xml). cookbook_import makes it; show and list read
  it. A changed add-on is read again. No tool writes there (paths.check).
  Here: import 1.7 s, show 0.04 s.
- A cookbook name may be written with - or _ ("texturizer-v2" is
  texturizer_v2) in import, show, approve, run, probe and export.

### Cost

No new start-up read. The new tool `cookbook_probe` is in the `porting`
group (not lean, not in the static base). With no cookbook installed, the
base listing is the same.
